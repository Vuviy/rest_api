● Відмінне питання — це наступний рівень розуміння версіонування. Поясню, що зазвичай означає «різні версії», які є патерни в індустрії, і як це підключити
  саме до того, що ми побудували.

  Спершу: що взагалі «відрізняється» між версіями?

  За частотою в реальних API:

  1. Форма відповіді (найчастіше ~80%): перейменоване поле (title → name), нова структура (author: "Іван" → author: {id, name}), додане/прибране поле.
  2. Форма запиту: інша валідація, нові обов'язкові поля.
  3. Поведінка: інша пагінація, інші дефолти, фільтри.
  4. Набір ендпоінтів: щось з'явилось/зникло.

  Найважливіше усвідомити: бізнес-логіка зазвичай та сама («дістати книги з БД»), а різниться представлення. Тому хороші рішення відокремлюють що ми дістаємо
  від як це показуємо.

  Три патерни (від найпростішого до «золотого стандарту»)

  Патерн A — Versioned Transformers / Presenters (рекомендую для тебе)

  Один контролер + один сервіс (логіка), але окремий «трансформер» на версію форматує відповідь.
  - BookTransformerV1 → {id, title, author}
  - BookTransformerV2 → {id, name, author: {...}}

  Контролер бере дані з сервісу і віддає їх потрібному трансформеру за версією з атрибута (api_version, який ми вже кладемо!). Нуль if-ів у логіці, нуль
  дублювання сервісу.
  ✅ Ідеально для різниці у формі відповіді (найчастіший випадок).

  Патерн B — Versioned Controllers

  Окремі класи контролерів: Controller\V1\BookController, Controller\V2\BookController. Роути ведуть на потрібний.
  ✅ Коли версії розходяться сильно (різна поведінка, різні ендпоінти).
  ❌ Дублювання оркестрації; спільне треба виносити в сервіси.

  Патерн C — «Stripe-style» transformation chain (як роблять найкращі)

  Stripe тримає один сучасний код, а для старих клієнтів застосовує ланцюг маленьких оборотних трансформацій, що «відкочують» нову відповідь до старого
  формату. Кожна breaking-зміна = одна маленька трансформація з датою.
  ✅ Масштабується на десятки версій без хаосу.
  ❌ Складно; виправдано для довгоживучих публічних API. Тобі поки не треба — але знай, що так буває.

  Як це підключити до НАШОЇ архітектури

  Ключ у тебе вже є: версія лежить в $request->getAttribute('api_version'). Це і є гачок. Для патерну A ескіз (ілюстрація, не комітимо):

  // інтерфейс
  interface BookTransformer {
      public function transform(array $book): array;
  }

  // дві реалізації
  final class BookTransformerV1 implements BookTransformer {
      public function transform(array $book): array {
          return ['id' => $book['id'], 'title' => $book['title'], 'author' => $book['author']];
      }
  }
  final class BookTransformerV2 implements BookTransformer {
      public function transform(array $book): array {
          return ['id' => $book['id'], 'name' => $book['title'],            // title → name
                  'author' => ['name' => $book['author']]];                // плоский → вкладений
      }
  }

  // фабрика обирає за версією (мапа version → transformer)
  final class BookTransformerFactory {
      public function for(int $version): BookTransformer {
          return match ($version) {
              2 => new BookTransformerV2(),
              default => new BookTransformerV1(),   // v1 = дефолт
          };
      }
  }

  А в контролері — один рядок вибору, без розгалуження логіки:
  public function list(Request $request): Response {
      $books = $this->service->all();                              // логіка — одна на всі версії
      $version = $request->getAttribute('api_version');           // вже встановлено middleware
      $transformer = $this->transformers->for($version);
      return new Response(array_map($transformer->transform(...), $books));
  }

  Краса: додати v3 — це новий трансформер + рядок у match. Сервіс, роути, middleware не чіпаються. Це пряме продовження наших рішень (api_version на запиті +
  «версія їде даними»).

  ▎ Якщо колись розійдеться й запит (інша валідація) — той самий підхід, але з версійними DTO/валідаторами, обраними за api_version.

  Коли який патерн брати (правило великого пальця)

  - Різна відповідь → Патерн A (трансформери). Почни звідси.
  - Різна поведінка/ендпоінти → Патерн B (версійні контролери), роути ведуть на різні класи.
  - Десятки версій публічного API → Патерн C (Stripe).

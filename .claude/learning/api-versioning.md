# Learning Note: API Versioning System

> Підсумкова навчальна нотатка по фічі. Мета — щоб через місяць ти відновив **хід думки**, а не лише код.
> Пов'язані документи: `specs/api-versioning.spec.md`, `decisions/0001-api-versioning-strategy.md`, `tasks/api-versioning.tasks.md`.

---

## 1. Проблема простими словами

API мав одну версію, «вшиту» в шляхи (`/api/v1/...`), а `Router` ставився до версії як до звичайного тексту в URL. Треба було зробити версію **окремою керованою сутністю**: щоб клієнт міг обрати версію трьома способами (URL, заголовок `X-API-Version`, `Accept`), щоб стара версія попереджала про застарівання (Deprecation/Sunset), і — головне — **щоб поява v2 не зламала жодного v1-клієнта**.

Ключова ідея, яку варто запам'ятати: **версіонування — це про еволюцію контракту без розриву зі старими споживачами**. Усе інше (стратегії, заголовки) — інструменти на службі цієї єдиної мети.

## 2. Execution flow (як запит проходить систему ПІСЛЯ змін)

```
HTTP-запит
   │
   ▼
index.php ──► bootstrap.php (DI) ──► routes/api.php ──► Router::dispatch()
   │                                                        │ матчить шлях регуляркою
   │                                                        ▼
   │                                         MiddlewareDispatcher (рекурсивний ланцюг)
   │
   ▼  ── ВХІД (in) ───────────────────────────────────────────────────►
   1) VersionMiddleware
        • VersionResolver.resolve(request):
            URL має /api/vN/ ? → версія = N   (заголовки ігноруються)
            інакше → X-API-Version → Accept;version → default(1)
            невідома версія → fallback на default
        • request.setAttribute('api_version', N)
   2) JwtMiddleware (auth; кидає виняток, якщо токен невалідний)
   3) RateLimitMiddleware (лише на list)
        │
        ▼ КОНТРОЛЕР (BookController)
        • бере дані з BookService (логіка — одна на всі версії)
        • transformer = factory.for(api_version)   ← гачок версії
        • форматує відповідь під версію (v1 identity / v2 renamed+nested)
        │ повертає Response
        ▲
   ── ВИХІД (out) ◄──────────────────────────────────────────────────
   3') RateLimitMiddleware → дописує X-RateLimit-*
   1') DeprecationMiddleware
        • читає api_version (вже встановлено на вході)
        • версія застаріла (є в config 'deprecated') ?
            → +Deprecation: true, +Sunset: <HTTP-date>, +Link: <migration guide>
   │
   ▼
Response::send()  → клієнт
```

**Три «подорожі» дають однаковий результат різними стратегіями:**

| Запит | Джерело версії | Контролер | Deprecation |
|---|---|---|---|
| `GET /api/v1/books` | URL → 1 | v1-форма | ✅ (v1 застаріла) |
| `GET /api/v2/books` | URL → 2 | v2-форма (`name`, вкладений author) | ні |
| `GET /api/books` + `X-API-Version: 1` | заголовок → 1 | v1-форма | ✅ |
| `GET /api/books` (без заголовків) | default → 1 | v1-форма | ✅ |
| `GET /api/books` + `Accept: ...;version=2` | Accept → 2 | v2-форма | ні |

Зверни увагу: рядки 1 і 3 ідентичні за результатом — це і є вимога «всі стратегії працюють однаково». Досягнуто тим, що **`api_version` встановлюється на ВСІХ шляхах**, тож контролер і `DeprecationMiddleware` не знають і не цікавляться, *як* саме обрали версію.

## 3. Чому саме так (рішення + відкинуті альтернативи)

Повне обґрунтування — в ADR-0001. Стисло, з акцентом на *чому*:

### 3.1. Дві сім'ї шляхів замість «вирішення конфлікту»
URL-версія (`/api/vN/`) і header-версія (`/api/`) **ніколи не діють на одному шляху**. Це усуває конфлікт «URL каже одне, заголовок інше» **як клас проблеми**, а не лікує кожен випадок `if`-ами.
> 🧠 Принцип: **проєктуй так, щоб погані стани були неможливими**, а не так, щоб їх обробляти.

### 3.2. Фіксований default замість «найновіша»
`/api/books` без версії → завжди v1 (фіксовано). Якби default = «найновіша», реліз v3 **раптово** переніс би всіх нейтральних клієнтів на v3 і поламав би їх. Фіксований default = свідома, а не випадкова міграція.

### 3.3. Пріоритет `X-API-Version > Accept`
Явний заголовок однозначний і простий у дебагу; `Accept` — це перевантаження механізму, що взагалі-то про формат. Тому явне б'є неявне (так дрейфують Stripe/GitHub).

### 3.4. Резолв = чисте ядро (`VersionResolver`) + тонка оболонка (`VersionMiddleware`)
**Відкинуто:** запхати парсинг прямо в `Router` чи в `handle()`. Чому окремий чистий клас — у п.5.

### 3.5. Deprecation = окремий response-middleware
**Відкинуто:** дописувати заголовки в кожному контролері (дублювання + забування). Один middleware = одне місце істини.

### 3.6. Routing: усі сім'ї → ті самі контролери (без реєстру)
Спершу ADR планував «реєстр version→handler». Але оскільки v1/v2 ділять бізнес-логіку, виявилось, що **достатньо мати версію на запиті** — реєстр не потрібен. Спростили, коли реальність дозволила (YAGNI). ADR оновлено чесно.

### 3.7. Розбіжність версій через Transformers (Strategy+Factory)
**Відкинуто:** `if ($version==2)` у контролерах (анти-патерн — розмазування версії). Натомість логіка форми винесена в окремі класи, обрані фабрикою.

## 4. Недоліки та технічний борг (чесно)

- **`Router::put()` був зламаний** — приймав middleware, але не зберігав → PUT йшли **без auth**. Полагодили (крок 0), але це симптом: 5 майже однакових методів роутера дрейфують. Кандидат на рефакторинг у єдиний `addRoute()`.
- **psalm baseline брудний** (~355 помилок: нетипізований `$routes`, `$_SERVER`, `callable $next → mixed`). Наш код чистий *відносно* baseline, але проєкт не «зелений». Окремий тікет.
- **`UnusedClass`/`MissingOverride` на наших middleware** — false-positives: psalm сканує лише `src/`, а реєстрація в `bootstrap.php` йому не видна. Рішення на майбутнє: psalm-baseline або інший спосіб реєстрації.
- **`parseUrlVersion` прив'язаний до префіксу `/api`** (захардкоджено в regex). Зміна базового шляху вимагатиме правки.
- **v2 відрізняється лише відповіддю.** Інша валідація запиту вимагала б версійних DTO/валідаторів (той самий патерн, інший шар).
- **Deprecation-заголовки не з'являться на помилкових відповідях** (напр. 401): помилки будуються в `ExceptionHandler` поза ланцюгом middleware. Консистентно з rate-limit заголовками, але варто знати.
- **Auth став breaking change** (прибрано `/api/v1/auth` → лише `/api/auth`). Backward compatibility для auth НЕ збережена; це задокументовано в migration guide, але старі клієнти зламаються.
- **`BookService` слабко типізований** (`array`), тому контролер тримає версію через `@var`-анотацію.

## 5. Патерни для запам'ятовування

| Патерн | Де застосували | Де ще зустрічається в індустрії |
|---|---|---|
| **Functional core / imperative shell** | `VersionResolver.decide()` (чисте) + `resolve()`/middleware (I/O) | тестовані ядра в DDD, Elm-архітектура, Redux reducers |
| **Strategy** | `BookTransformer` (V1/V2 взаємозамінні) | сортування, платіжні провайдери, серіалізатори |
| **Factory** | `BookTransformerFactory.for(version)` | DI-контейнери, парсери, драйвери БД (тут же `ConnectionFactory`) |
| **Middleware «цибуля»** | Version (in) / Deprecation (out) навколо `$next` | Express, Laravel, ASP.NET, PSR-15 |
| **Configuration vs logic** | `config/versioning.php` (дані) ↔ resolver/middleware (поведінка) | feature flags, `config/` будь-якого фреймворку |
| **Data-driven declarations (DRY)** | цикл по `$versionPrefixes` × `$bookRoutes` | генерація CRUD-роутів, табличні тести |
| **Make illegal states unrepresentable** | дві сім'ї шляхів → конфлікт неможливий | типобезпечне моделювання, sum types |
| **Open/Closed (SOLID)** | додати v3 = новий transformer + рядок `match` | плагінні системи |

**Наскрізний мета-урок:** добра архітектура робить **майбутні зміни дешевими**. Коли v2 мала по-справжньому розійтися з v1, це коштувало майже нічого — бо гачок `api_version` був закладений заздалегідь. Поганий дизайн карає при кожній зміні; добрий — винагороджує.

**Мета-урок №2 — про інструменти:** «зелено» ≠ «нуль рядків у виводі». На брудному baseline критерій інший: *мій код не додає реальних проблем*. І це треба **доводити** (порівнянням категорій), а не відчувати.

**Мета-урок №3 — про ітеративність:** ми двічі поверталися й переглядали ранній код (`VersionResolver` отримав URL; ADR оновлено). Це не провал планування — це нормальна еволюція, коли нове питання виявляє вимогу. Головне — тримати ADR/нотатки правдивими.

## 6. Питання для самоперевірки (відповідай з голови, без підглядання)

1. Чому `/api/v99/books` дає `404`, а `X-API-Version: 99` — fallback на v1? Де проходить межа між роутингом і резолвом?
2. Назви точний порядок резолву версії і поясни, чому URL — найвищий, а Accept — нижчий за `X-API-Version`.
3. Чому `DeprecationMiddleware` читає версію *після* `$next`, а `VersionMiddleware` встановлює її *до*? Чи спрацювало б, якби порядок middleware у списку був зворотний?
4. Скільки місць довелось би змінити, щоб додати v3, яка інакше форматує книги? А якби v3 ще й мала іншу валідацію запиту?
5. Чому ми НЕ робили «реєстр version→handler», хоча ADR його планував? Який принцип це ілюструє?
6. Чим `versioned resource` (книги) відрізняється від `version-neutral infrastructure` (auth)? За яким критерієм ти класифікував би новий `/api/health`?
7. Який принцип SOLID порушив би `if ($version === 2)` прямо в контролері замість трансформера?
8. Чому фіксований default безпечніший за «завжди найновіша версія» з точки зору backward compatibility?

## 7. Файлова карта фічі (для швидкого повернення)

- `config/versioning.php` — політика версій (supported, default, deprecated, sunset).
- `src/Versioning/VersionResolver.php` — чисте ядро резолву (URL → header → Accept → default).
- `src/Versioning/VersionMiddleware.php` — встановлює `api_version` на запит.
- `src/Versioning/DeprecationMiddleware.php` — дописує Deprecation/Sunset/Link на виході.
- `src/Versioning/Transformers/*` — форма відповіді per version (Strategy + Factory).
- `routes/api.php` — генерація роутів циклом по префіксах версій.
- `src/Router.php` — фікс `put()` (middleware тепер зберігаються).
- `bootstrap.php` — DI-прив'язки всього вищезгаданого.
- `docs/migration-v1-to-v2.md` — клієнтський гайд міграції.
